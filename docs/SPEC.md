# Hatch 仕様書

Discord と Web パネルから、Pterodactyl（将来は Pelican も）のゲームサーバーを「一回の指示で」作成・公開・監視・運用するための基盤です。

- 対象の構成: Proxmox VE（オーケストレーターを LXC で動かす）/ Pterodactyl + Wings / Tailscale / Linode（edge: HAProxy・nginx）/ Cloudflare / Uptime Kuma
- ライセンス: MIT（公開リポジトリ前提。秘密情報はリポジトリに入れない）
- 画面: Apple iOS 27 風（見やすさ優先・どの項目にも2タップ以内）。詳細は `docs/UI.md`
- 実装の進め方: `AGENTS.md` と `docs/TASKS.md`

---

## 1. 全体構成

```
 利用者 ─ Discord ─┐                   ┌─ Pterodactyl パネル（Application / Client API）
 利用者 ─ Web ─────┼─► オーケストレーター ─┼─ Cloudflare API（DNS のみ）
                   │   （Proxmox の LXC）  ├─ Uptime Kuma（Socket.IO / /metrics / Webhook）
                   │   API・ジョブ・Bot    ├─ Object Storage（バックアップ）
                   │   PostgreSQL（正本）   └─ edge エージェント ◄─ 設定を取りに来る
                   │                                     │
 プレイヤー ─► edge.example.net（edge-1 / edge-2）── Tailscale ──► Wings ノード
```

| 部品 | 置き場所 | 役割 |
|---|---|---|
| オーケストレーター | Proxmox の LXC（本リポジトリのインストーラーで作成） | API、Web パネル配信、ジョブ実行、Discord Bot、スケジューラー |
| PostgreSQL | 同じ LXC | 唯一の正本。ジョブキューも兼ねる（Redis 不要） |
| edge エージェント | Linode の edge-1（東京）と edge-2（大阪） | HAProxy 設定を取得・検証・適用し、状態を報告 |
| Wings | 既存のノード | ゲームサーバー本体。割当 IP は Tailscale の 100.x |

**以前の設計からの変更点**

1. オーケストレーターの置き場所を Linode から Proxmox の LXC に変更。edge は「入口」だけに専念させる。
2. edge への設定反映を「オーケストレーターが送り込む」から「エージェントが取りに来る」に変更。オーケストレーターや自宅回線が止まっても edge は最後の設定で動き続け、edge-2 も自然に最新を保てる。SSH 鍵をオーケストレーターに置かなくてよい。
3. Web パネルの公開は Cloudflare Tunnel か、edge の nginx から Tailscale 経由で中継する（どちらも自宅側のポート開放不要）。オーケストレーターの API をインターネットに直接公開しない。
4. 問い合わせ窓口（`/support`）は見送り。

## 3. デプロイの流れ

1つの「ジョブ」として順に実行します。各手順は「実行」と「取り消し」を対で持ち、失敗したら完了済みの手順を逆順に取り消します。

| # | 手順 | 取り消し |
|---|---|---|
| 1 | 検証（名前・上限・予約名・利用規約への同意・アカウント状態） | — |
| 2 | スロット確保（`slots` を `free` → `assigned` に条件付き UPDATE。0行なら競合） | `free` に戻す |
| 3 | パネルのユーザーを確認（なければ作成） | 新規作成した場合のみ削除 |
| 4 | ノード選択 → パネルにアロケーション作成 → サーバー作成（`external_id` にパネル側のIDを入れる） | サーバーとアロケーションを削除 |
| 5 | edge 設定の新しい版を作成し、両 edge の適用を待つ（最大60秒） | 前の版に戻す |
| 6 | DNS：CNAME（コメント `hatch slot=<port>`、プロキシ無効）。事前作成済みの枠では確認のみ | 事前作成でなければ削除 |
| 7 | DNS：SRV（Minecraft 系のみ）。同上 | 同上 |
| 8 | 起動し、edge 経由で応答を確認 | 停止 |
| 9 | バックアップのスケジュール作成、期限設定 | スケジュール削除 |
| 10 | Uptime Kuma に監視を追加（Webhook 通知付き） | 監視を削除 |

- **ドライラン**：同じ手順を「何を作るか」の一覧として返すだけのモード。Web の作成画面の最終ステップはこれを表示してから実行する。
- **重複実行の防止**：Discord のインタラクション ID や Web のリクエスト ID を `jobs.idempotency_key` に入れる。
- **ジョブキュー**：`SELECT … FOR UPDATE SKIP LOCKED` で1件ずつ取り出す。ワーカーが落ちても `locked_at` が古いジョブは再開できる（各手順は「既に作ってあれば使う」書き方にして、何度実行しても同じ結果にする）。

### 削除とゴミ箱

- 削除 → サーバーを停止し、監視を一時停止、edge の公開を止め、DNS を外して **ゴミ箱**（72時間）へ。
- ゴミ箱の間は **名前とスロットを予約したまま**（スロットは `held`）。元に戻すと DNS・edge・監視も復元する。
- 72時間後または「完全に削除」で：最終バックアップ（30日保管）→ 監視削除 → DNS 削除 → edge 設定から除外 → パネルから削除 → スロットと名前を解放（事前作成した DNS は枠に残す）。完全削除は名前の入力で確認する。

## 3A. アドレス（ドメイン・IP・アドレス枠）

管理者が「どのポートを、どのホスト名で公開するか」を先に決めておき、利用者は作成時に空きを選ぶだけにします。

```
ドメイン（nuids.jp ほか。Cloudflare のゾーン）
 ├─ IP の紐付け（A レコード）  edge.nuids.jp → 使用中の edge に追従／固定の IP
 └─ アドレス枠   25560–25569 / mc{nn}trt / 対象外 25560 / 全員で共有
      └─ スロット  25561 = mc01trt.nuids.jp（空き・使用中・ゴミ箱・停止・対象外）
```

- **ドメイン**：複数登録できる（例 nuids.jp と、もう1つのドメイン）。登録時に Cloudflare のゾーンを確認し、`edge.<ドメイン>` を「使用中の edge に追従」で作る。1つを既定にする。
- **IP と紐付け**：edge-1・edge-2 や予備の IP を登録し、ホスト名 → IP の A レコードを作る。「追従」の紐付けは edge 切り替えでまとめて書き換わる。
- **アドレス枠**：ポート範囲とホスト名の決め方（テンプレート）の組。記号は `{n}` `{nn}` `{nnn}` `{port}` `{server}`。番号は「開始番号 ＋（ポート − 開始ポート）」で、対象外のポートがあってもずれない。
  - 例：`25560–25569`、`mc{nn}trt`、開始番号0、対象外25560 → 25561=mc01trt … 25569=mc09trt
  - 例：開始番号1で対象外なし → 25560=mc01trt … 25569=mc10trt
  - `{server}` の枠はサーバー名がホスト名になる（利用者ごとの専用枠に向く）
- **DNS の形**：既定は `edge.<ドメイン>` への CNAME（edge を切り替えても枠のレコードは変わらない）。IP 直指定も選べるが、edge 切り替え時に全レコードの書き換えが必要。SRV は Minecraft 系のみ。
- **事前作成**：固定ホスト名の枠は DNS を先にまとめて作れる。割り当てた瞬間から接続でき、DNS の伝播待ちがない。
- **使える人**：全員で共有、または特定のユーザー専用。Discord ロールで専用枠を自動作成することもできる。
- **25565 番**：以前は予約していたが、枠に含めれば普通に使える（SRV が不要なポート。デモでは mc05trt）。
- 使用中・ゴミ箱のスロットがある間は、その枠のテンプレート・ドメイン・開始番号を変更できず、該当ポートを範囲から外せない。

詳しい規則は `docs/IMPLEMENTATION.md` 4章。

## 4. アカウントとゲームパネル

- パネルのユーザー作成時に、同じユーザー名・メールでゲームパネルにもユーザーを作る（Application API）。
- パスワードはパネルで設定・変更された瞬間に、同じ値をゲームパネルにも設定する。**パネルは平文を保存しない**。
- ユーザー名はゲームパネルの制約に合わせて `^[a-z0-9][a-z0-9_.-]{2,31}$`。Discord 名が合わない場合は初回に選ばせる。
- ゲームパネルは SSO を標準で持たないため、この「同期方式」を採用。二段階認証の解除など API にない操作はゲームパネルの管理画面で行う。
- **パネルアダプター**：ゲームパネルとのやり取りは `PanelAdapter`（ユーザー・サーバー・アロケーション・サブユーザー・バックアップ・スケジュール・ファイル・電源）に閉じ込める。Pterodactyl と Pelican の差はここで吸収し、将来の移行に備える。

### Discord ロール連携

- ロールとパネル上の扱い（ロール・プラン・台数上限・専用のアドレス枠）を対応表で管理。
- ロールが付いたら利用開始（利用規約への同意が済むまで作成は不可）。外れたら通知し、7日後に所有サーバーを停止。

### 利用規約と違反対応

- 規約は版ごとに保存し、同意を記録。新しい版が出たら次回ログイン時に再同意を求める。
- 違反は「警告」「サーバー停止」「アカウント停止」を記録し、理由を所有者に通知。停止中のサーバーは所有者から起動できない。

### 退会とデータの削除

**方針：退会の申請から7日後に削除する。7日以内なら本人が取り消せる。**

| 時点 | 起きること |
|---|---|
| 申請（設定 → 退会する。ユーザー名の入力で確認） | 所有するサーバーをすべて停止し、監視を一時停止。新しい作成はできない。共同管理者として参加しているサーバーから外す。本人に DM で「◯月◯日に削除します・取り消し方」を送る |
| 申請から6日後 | 「明日削除します」を DM で通知 |
| 7日後（削除ジョブ） | 所有サーバーを完全に削除（**最終バックアップは作らない**。既存のバックアップも削除）→ DNS・監視・独自ドメイン・edge 設定を削除 → ゲームパネルのアカウントを削除 → セッション・二段階認証・表示設定・アップロードした背景・通知設定を削除 → ユーザーの行は ID だけを残し、名前・メール・Discord ID を消す（`deleted-xxxxxxxx` に置き換え） |
| 取り消し（7日以内） | 退会前の状態に戻す。サーバーは停止したまま（本人が起動する） |

- 操作ログは「退会したユーザー」と表示される形で1年間残す（不正利用の調査のため）。操作ログの `target` や `detail` にはユーザー名・メール・Discord 名を書かない決まりにし、表示時に `actor_id` から名前を引く。
- 違反でアカウント停止中の人が退会した場合は、Discord ID のハッシュ（`banned_identities`）だけを残し、同じ Discord アカウントでの再登録を防ぐ。
- 最後の管理者は退会できない（先に別の管理者を任命する）。
- Discord ロールが外れた場合（利用資格の喪失）は退会ではなく「7日後にサーバー停止」。削除は期限切れと同じ流れ（停止から14日後にゴミ箱）。
- プライバシーポリシーには「退会後7日で削除」「操作ログは匿名化して1年保存」「ゲームパネル・DNS・監視など外部サービスからも削除」を明記する。

## 5. 監視と自動復旧

- 監視の追加・一時停止・削除は Uptime Kuma の内部 Socket.IO API（Python なら `uptime-kuma-api2`）。**非公式 API のため Kuma のバージョンを固定**し、更新前に CI で確認する。
- ワーカーは Kuma への接続を1本だけ保持して使い回す（ログインの繰り返しによる制限を避ける）。
- 状態の読み取りは `/metrics`（API キー）を30秒ごとに取得してキャッシュ。Kuma 本体は利用者に見せない。
- ダウン通知は Kuma の Webhook → オーケストレーター。URL に秘密トークンを含め、Tailscale 内からのみ受け付ける。
- 自動再起動の条件：自動再起動がオン、メンテナンス中でない、手動停止中でない、利用停止中でない、パネル上の状態が `starting` ではない、直近1時間で3回未満。超えたら止めて通知。


### 自己監視（オーケストレーター自身の監視）

オーケストレーターが止まると、自分で「止まった」と知らせることができません。そのため **外から見る仕組み** と **中で見る仕組み** を分けます。

| 仕組み | 内容 | 通知の経路 |
|---|---|---|
| systemd | 各プロセスは `Restart=always`。落ちても3秒後に自動で起動 | — |
| 生存報告 | worker・scheduler・bot は30秒ごとに `component_heartbeats` を更新 | — |
| `/api/health` | DB に接続できるか（認証なし、最小限）。`update` の起動確認にも使う | — |
| `/api/health/full` | DB・各プロセスの報告の新しさ（90秒）・バージョンの一致・待ちジョブの遅れ・取り消せなかったジョブ・edge の報告・ディスク容量。`PD_HEALTH_TOKEN` が必要。異常なら 503 | — |
| Uptime Kuma：HTTP 監視 | `/api/health` を1分ごと。応答がなければ停止 | **Kuma → Discord の Webhook（直接）** |
| Uptime Kuma：キーワード監視 | `/api/health/full` に `"status":"ok"` が含まれるか。軽い異常も検知 | 同上 |
| Uptime Kuma：Push 監視×3 | worker・scheduler・bot がそれぞれ1分ごとに送る。2分届かなければ停止 | 同上 |
| 管理画面「システムの状態」 | `/api/health/full` と同じ内容を表示 | — |

- 自己監視の通知は、オーケストレーターを経由せず Kuma に設定した Discord の Webhook から直接、管理者用チャンネルへ送る。
- Kuma がオーケストレーターと同じ Proxmox ホスト（同じ電源・回線）にあると、停電や回線断をまとめて見逃す。Kuma は別の場所（Linode など）に置くか、少なくとも Kuma 自身を外から見る仕組み（edge-2 からの簡単な確認など）を用意する。
- 初期設定画面で保存した後に、これらの監視を Kuma に登録する（既にあれば更新）。

## 6. edge（入口）

- edge-1（東京・使用中）と edge-2（大阪・待機）。`edge.example.net` の A レコードを使用中の方に向ける。
- 各サーバーの CNAME・SRV は `edge.example.net` を指すので、切り替えは A レコード1つの書き換えで済む（TTL 60秒）。
- 自動切り替え：オーケストレーターと Uptime Kuma の両方が「使用中の edge が3回続けて応答しない」と判断したときだけ切り替える（片方の回線不調による誤切り替えを防ぐ）。
- HAProxy の設定は DB から生成し、エージェントが検証（`haproxy -c`）→ 原子的に差し替え → reload。reload に失敗したら元に戻す。
- 接続保護：IP ごとに同時20接続・10秒に30回まで、サーバーごとに最大500接続、超えた IP は10分遮断。
- Linode のファイアウォールで、アドレス枠のポート範囲と 80/443 だけを開ける。
- **UDP のゲーム**（Palworld など）は HAProxy では中継できないため、エージェントが nftables で転送する（同じ設定の版に含める）。監視はパネル上の状態を Kuma の Push 監視に送る方式。

```haproxy
frontend fe_30012
    bind :30012
    mode tcp
    maxconn 500
    stick-table type ip size 100k expire 10m store conn_cur,conn_rate(10s)
    tcp-request connection track-sc0 src
    tcp-request connection reject if { sc0_conn_cur gt 20 } || { sc0_conn_rate gt 30 }
    default_backend be_storia

backend be_storia
    mode tcp
    server wings 100.64.0.12:30012 send-proxy-v2 check check-send-proxy
```

## 6A. 画面：表示のカスタマイズと端末対応

### 背景

- 利用者ごとに背景を選べる：「既定（管理者が選んだもの）」「なし」「用意した背景（オーロラ・夕焼け・海・森・ブロック。ライト・ダークで色が変わる）」「自分の写真」。
- 調整：「見やすさ」（背景の上に画面の地の色を重ねる量。0〜85%）と「ぼかし」（0〜40px）。
- 写真は20MB まで。サーバー側で長辺2560px の WebP（3MB 以下）に変換し、**位置情報などのメタデータを取り除いて**保存する。保存先は `PD_DATA_DIR/uploads/`。他の利用者からは見えない。
- 管理者は「この背景を全員の既定にする」ができる。自分で選んだ人の設定は変わらない。
- 一覧やカードは不透明のまま（文字の読みやすさを優先）。背景に直接載る見出しには、地の色の縁取りを付ける。

### 対応する画面サイズ

| 幅 | 想定する端末 | 配置 |
|---|---|---|
| 〜359px | 小さいスマホ、フォルダブルを閉じた状態のカバー画面 | 下のタブバー。余白・文字・タイルを詰める |
| 360〜699px | 一般的なスマホ、フォルダブルを開いた縦持ち（670px 前後） | 下のタブバー。タイルは本文の幅が600px 以上なら4列 |
| 700〜1099px | フォルダブルを開いた状態、タブレット | 細めのサイドバー（248px） |
| 1100px〜 | PC | サイドバー（300px） |
| 高さ500px 以下の横向き | 横向きのスマホ | 見出しを小さく、シートは画面いっぱい |
| 左右2画面（折り目あり） | 折り目のある端末 | 左の画面にサイドバー、右の画面に本文とシート。折り目に文字を置かない |
| 上下2画面 | テーブルトップの姿勢 | シートを下の画面に出す |

- スマホのブラウザのアドレスバーの伸び縮みに合わせるため、高さは `100dvh` を使う。キーボードが出たときに入力欄が隠れないよう `interactive-widget=resizes-content` を指定。
- ノッチやホームバーの領域（safe area）に部品を置かない。
- 入力欄の文字は16px 以上（iPhone で入力時に拡大されないように）。

## 7. 予想される不具合と対策（見直し結果）

| # | 起きうること | 原因 | 対策（設計に反映済み） |
|---|---|---|---|

## 8. 導入と更新

### 導入（Proxmox VE ホストのシェルで1行）

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/<ユーザー>/hatch/main/ct/hatch.sh)"
```

Proxmox VE Helper-Scripts と同じ流れで、標準設定か詳細設定を選ぶと以下を自動で行います。

1. Debian 13（なければ 12）のテンプレートを取得
2. 非特権 LXC を作成（nesting 有効、tun デバイス付き、起動時に自動開始）
3. コンテナ内で PostgreSQL・Python・Tailscale を導入、DB と設定ファイル（秘密値は自動生成）を作成
4. GitHub Releases から最新版を取得して配置、DB を移行、systemd で起動
5. コンテナ内に `update` と `hatch-setup` コマンドを登録
6. パネルの URL と **初期設定コード** を表示

### 初期設定（ブラウザ）

外部サービスの値（ゲームパネル・Cloudflare・Uptime Kuma・Discord）は、コンテナの中ではなく **パネルの初期設定画面** で入力する。

- 初期設定が終わるまでは、パネルを開くと初期設定画面になる。操作には初期設定コードが必要（パネルを先に開いた第三者に乗っ取られないため）。コードはインストールの最後に表示され、コンテナ内の `hatch-setup` でも再表示できる。
- 各ステップに「値の取り方」を表示し、**接続確認** で入力した値をその場で確かめる。
- Discord は、Bot トークンで Bot が参加しているサーバー・ロール・チャンネルを取得し、一覧から選ばせる（ID を手でコピーさせない）。Bot が未参加なら招待のリンクを出す。
- 最後に **管理者のロール**（必須）と利用者のロール（任意）を選ぶ。これで最初の管理者がログインできる（ロールの対応表が空でログインできない状態を作らない）。
- 保存すると自動で再起動し、ログイン画面に進む。
- 設定が壊れた（必須の値が無い）ときも、初期設定画面が再び開く。やり直したいときは `hatch-setup --reset`。

失敗したら作成途中のコンテナを自動で削除します（`PD_KEEP_ON_FAIL=1` で残せます）。

### 更新（コンテナ内で1行）

```bash
update            # 最新の安定版へ
update --check    # 確認だけ
update --channel beta
update --rollback [--restore-db]
```

流れ：リリース取得 → sha256 検証 → 展開 → 依存導入 → DB 退避 → 移行 → 切り替え → 再起動 → 死活確認（失敗なら自動で戻す）。リリースは3世代、DB の退避は10世代残します。

### テスト環境（ステージング）

本番と別に、テスト用のパネルを用意します（構成は `docs/ENVIRONMENT.md`）。

- オーケストレーターの LXC をもう1つ作り、`PD_INSTANCE=stg` にする。テスト用のパネル・Wings・edge・Discord Bot・Discord サーバーを使う。
- DNS は本番と同じゾーンでもよいが、アドレス枠のホスト名を `stg-mc{nn}` のように分け、`PD_INSTANCE` で互いに消し合わないようにする。
- リリースは「ベータ版（`v0.2.0-beta.1`）をテスト環境で `update --channel beta` → 確認 → 正式版を本番へ」の順にする。
- 実装を担当する AI の結合テストは、テスト環境の API キーだけを使う（本番のキーは渡さない）。

### リリースの作り方

`v0.2.0` のようなタグを push すると GitHub Actions が配布ファイルを作って公開します。`v0.2.0-beta.1` のように `-` を含むタグはベータ版になります。

## 10. 料金システム（将来）

今のうちに入れてある土台：`plans.price_jpy`（NULL は無料）、期限（`expires_at`）と延長の仕組み、操作ログ。追加時の想定：

- 決済は Stripe などの外部サービスに任せ、Webhook で「支払い完了 → 期限を延長」。カード情報は持たない。
- 自動更新・日割り・返金の方針は先に決める。
- 有料で提供する場合は、特定商取引法に基づく表記、プライバシーポリシー、利用規約の料金条項が必要。
